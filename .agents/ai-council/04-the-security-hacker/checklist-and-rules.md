# مصفوفة التهديدات وقائمة فحص الأمان واصطياد الثغرات (The Offensive Security & Edge-Case Constitution)
## خبير المجلس: زياد "زيرو داي" منصور (The Security Hacker)
## كود الدستور: `CHECKLIST-04-SECURITY-REDTEAM`

---

### المقدمة وفلسفة الـ Zero-Trust المطلقة
هذا الدستور هو سد الحماية الأخير والمحاكمة العسكرية لأي كود أو تصميم برمجي. كل سطر كود يُفترض أنه مخترق حتى يتم إثبات تحصينه بالدليل الرياضي والهجومي القاطع. لا توجد ثغرة صغيرة وثغرة كبيرة؛ كل ثغرة مهملة هي مفتاح يمنح المهاجم موطئ قدم للسيطرة الكاملة على السيرفر، تسريب البيانات، أو تدمير المنظومة بالكامل.

---

### مصفوفة الفحص الهجومي (35 فحصاً أمنياً صارماً):

#### أولاً: التحكم في الوصول والصلاحيات (Broken Access Control & IDOR)
1. **[SEC-01] اصطياد ثغرات الـ IDOR على مستوى السجلات (Record-Level Authorization):** هل يتم التحقق من أن المستخدم يمتلك السجل المطلوب فعلياً في كل استعلام (`WHERE id = :id AND tenant_id = :tenantId`)، أم يكتفي الكود بفحص أن المستخدم مسجل دخول فقط؟
2. **[SEC-02] العزل التام للمستأجرين (Multi-Tenant Data Isolation):** هل توجد سياسات عزل صارمة (مثل Row-Level Security في Postgres أو Tenant Scoping تلقائي في الـ ORM) تمنع تسريب بيانات منشأة إلى أخرى؟
3. **[SEC-03] حماية حقول الـ Mass Assignment:** هل تم تطبيق تصفية بيضاء صارمة (Strict Whitelisting / Schema Validation مثل Zod) تمنع تمرير حقول غير مصرح بها (مثل `role`, `is_admin`, `verified`) في طلبات الإنشاء والتعديل؟
4. **[SEC-04] فحص الصلاحيات متعددة المستويات (Horizontal & Vertical Privilege Escalation):** هل يستطيع مستخدم عادي الوصول إلى وظائف المديرين بتغيير مسار الـ API من `/user/profile` إلى `/admin/profile`؟
5. **[SEC-05] أمان واجهات الـ Webhooks والـ Callbacks:** هل يتم التحقق من توقيع الـ Webhooks الواردة من بوابات الدفع (HMAC Signature Verification) مع مفتاح سري قوي لمنع تزوير المعاملات المالية؟

#### ثانياً: المصادقة وإدارة الجلسات والتوكنات (Authentication & Session Hygiene)
6. **[SEC-06] بيئة تخزين التوكنات الآمنة (Secure JWT Storage):** هل يُمنع منعاً باتاً تخزين الـ JWT في الـ LocalStorage أو SessionStorage، واستخدام `HttpOnly, Secure, SameSite=Strict / Lax Cookies` بدلاً منها؟
7. **[SEC-07] التوقيع الآمن وتحديد خوارزمية التوكن (JWT Algorithm Hardening):** هل تم تقييد خوارزمية التشفير صراحة (مثل `RS256` أو `HS256`) ومنع هجوم الـ `alg: "none"` أو الخلط بين المفتاح العام والخاص؟
8. **[SEC-08] آلية إبطال التوكنات الفورية (Token Revocation / Blacklist):** هل توجد قائمة إبطال سريعة (Redis Blacklist) لإنهاء صلاحية الـ Refresh Token فوراً عند تسجيل الخروج أو تغيير كلمة المرور؟
9. **[SEC-09] تشفير كلمات المرور بحسابات استهلاك مكثفة (Password Hashing Standards):** هل يتم تجريد كلمات المرور وتشفيرها باستخدام `Argon2id` أو `bcrypt` بعامل تكلفة (Cost Factor) لا يقل عن 12 لمنع كسرها عبر الـ GPU Brute Force؟
10. **[SEC-10] حماية مسارات الدخول من التخمين (Brute-Force & Rate-Limiting):** هل مسارات تسجيل الدخول واستعادة كلمة المرور محمية بـ Rate Limiting صارم (أقل من 5 محاولات فاشلة لكل IP و Username قبل الحظر المؤقت)؟

#### ثالثاً: ثغرات الحقن ومعالجة المدخلات (Injection & Input Validation)
11. **[SEC-11] التحصين ضد الـ SQL / NoSQL Injection:** هل كافة استعلامات قاعدة البيانات بدون استثناء تستخدم الـ Parameterized Queries وتتجنب تجميع النصوص يدوياً (String Concatenation)؟
12. **[SEC-12] تطهير المدخلات من ثغرات الـ XSS (Cross-Site Scripting):** هل يتم تشفير وتطهير كافة البيانات المعروضة في الواجهة لمنع حقن أكواد جافاسكريبت خبيثة تسرق الجلسات أو تتلاعب بالصفحة؟
13. **[SEC-13] التحصين ضد الـ Server-Side Request Forgery (SSRF):** إذا كان النظام يقوم بتحميل صور أو روابط خارجية بناءً على طلب المستخدم، هل يتم فحص الـ IP والتحقق من أنه ليس IP داخلياً (مثل `127.0.0.1`, `169.254.169.254`, `10.0.0.0/8`)؟
14. **[SEC-14] أمان رفع الملفات وتسميتها (File Upload Hazards):** هل يتم فحص نوع الملف الحقيقي (Magic Bytes) وليس فقط الامتداد؟ وهل تُخزن الملفات المرفوعة على سيرفر تخزين خارجي (S3) مع منع تنفيذ أي سكريبت داخلها وتغيير أسمائها إلى UUID عشوائي؟
15. **[SEC-15] فحص ثغرات الـ Command Injection:** هل يُمنع منعاً باتاً استخدام دوال مثل `eval()`, `exec()`, `spawn()` لتمرير مدخلات يرسلها المستخدم مباشرة إلى نظام التشغيل؟

#### رابعاً: ثغرات التزامن والمنطق التجاري (Race Conditions & Business Logic)
16. **[SEC-16] اصطياد ثغرة الـ Race Condition في الأرصدة (Double-Spend Flaw):** هل المعاملات التي تخصم رصيداً، محفظة، أو تطبق كوبون خصم تستخدم Database Transactions مع `SELECT FOR UPDATE` لمنع سحب نفس القيمة في طلبيين متزامنين؟
17. **[SEC-17] فحص الحدود الرقمية السالبة والكسور (Integer Underflow / Negative Values):** هل يقبل النظام قيماً سالبة في حقول الكمية، الرصيد، أو السعر (مثل شراء `-5` منتجات للحصول على رصيد إيجابي)؟
18. **[SEC-18] التلاعب بترتيب الخطوات (Workflow Bypass):** هل يمكن للمستخدم القفز إلى خطوة تأكيد الدفع أو شحن الطلب دون المرور الفعلي بخطوة الدفع وتأكيد البنك؟
19. **[SEC-19] استغلال كوبونات الخصم المتكررة (Coupon Cycling Abuse):** هل يتم قفل كود الخصم بحساب العميل وسجل الدفع، لمنع تطبيق الكوبون مرة ثانية أثناء معالجة الطلب؟

#### خامساً: تسريب البيانات وإدارة الأسرار (Secrets Exposure & Information Leakage)
20. **[SEC-20] فحص تسريب المفاتيح في الكود (Secrets in Version Control):** هل يحتوي مستودع الكود (Git History) على أي مفتاح سري، شهادة SSL، أو كلمة مرور داتابيز مسجلة في الـ Commits السابقة؟
21. **[SEC-21] أمان حزم الواجهة الأمامية (Frontend Bundle Leaks):** هل تحتوي ملفات الـ Javascript في المتصفح على مفاتيح داخلية أو عناوين خوادم تطوير أو بيانات اعتماد إدارية؟
22. **[SEC-22] إخفاء تفاصيل الأخطاء والـ Stack Traces:** هل ترجع الخوادم في بيئة الإنتاج رسائل خطأ موحدة وعامة (Generic Error Messages)، وتمنع تسريب أسماء الجداول، استعلامات الـ SQL، أو أسطر الكود؟
23. **[SEC-23] تشفير البيانات الحساسة أثناء السكون (Data at Rest Encryption):** هل يتم تشفير بيانات البطاقات البنكية، الأرقام القومية، وأرقام الهواتف داخل قاعدة البيانات باستخدام خوارزميات معتمدة (`AES-256-GCM`)؟
24. **[SEC-24] التحصين ضد الـ Timing Attacks:** هل مقارنة التوكنات الحساسة وكلمات المرور والهاشات تتم باستخدام دوال زمنية ثابتة (`crypto.timingSafeEqual`) لمنع كشف الرموز عبر قياس زمن الاستجابة؟

#### سادساً: أمان الشبكة والترويسات وحجب الخدمة (Network, Headers & DoS)
25. **[SEC-25] ترويسات الأمان الإلزامية (HTTP Security Headers):** هل تم تفعيل حزمة `Helmet` وضبط ترويسات: `Content-Security-Policy (CSP)`, `X-Frame-Options: DENY`, `Strict-Transport-Security (HSTS)` لمنع هجمات الـ Clickjacking والـ MITM؟
26. **[SEC-26] تقييد سياسة الـ CORS الصارمة:** هل يتم قصر سياسة الـ CORS على النطاقات الموثوقة حصراً، ويُمنع منعاً باتاً وضع `Access-Control-Allow-Origin: *` مع تفعيل الـ Credentials؟
27. **[SEC-27] حماية مسارات الـ API من هجمات الـ DoS (Rate Limiting Tiers):** هل توجد مستويات متعددة من الـ Rate Limiting (على مستوى الـ IP، على مستوى الـ User ID، وعلى مستوى العمليات الحساسة)؟
28. **[SEC-28] تحديد حجم الـ Payload الأقصى (Body Size Limits):** هل تم ضبط خوادم الويب لرفض أي Payload يتجاوز حجماً معقولاً (مثل 1MB للـ JSON و 10MB للملفات) لمنع استنزاف ذاكرة الخادم وشل حركة الـ Event Loop؟

#### سابعاً: أمان سلاسل التوريد والاعتمادات الخارجية (Supply Chain & Dependencies)
29. **[SEC-29] تدقيق الحزم الخارجية (Automated Dependency Audit):** هل يتم فحص مكتبات `npm / pip` دورياً عبر `npm audit` أو `Snyk` للتأكد من خلوها من ثغرات معروفة (High/Critical CVEs)؟
30. **[SEC-30] تثبيت إصدارات الحزم بدقة (Lockfile Integrity):** هل يتم تثبيت إصدارات المكتبات الدقيقة عبر `package-lock.json` لمنع تحميل إصدارات خبيثة عند إعادة بناء الخوادم؟
31. **[SEC-31] التحقق من أمان التكامل مع الـ AI Providers:** هل يتم تشفير وفلترة الرسائل المرسلة إلى نماذج الـ LLM لمنع تسريب بيانات العملاء السرية في تدريب النماذج العامة؟

#### ثامناً: السجلات الجنائية والاستجابة للحوادث (Audit Logging & Incident Response)
32. **[SEC-32] السجلات غير القابلة للتلاعب (Immutable Audit Trail):** هل يتم تسجيل كافة العمليات الإدارية الحساسة (تعديل الصلاحيات، عمليات الحذف، الوصول للبيانات البنكية) في سجلات لا يمكن حذفها حتى بواسطة المدير؟
33. **[SEC-33] تنظيف السجلات من البيانات السرية (Log Sanitization):** هل تتأكد وحدات الـ Logger من حجب كلمات المرور وأرقام البطاقات وأرقام الهواتف والـ JWT Tokens من ملفات الـ Logs؟
34. **[SEC-34] استراتيجية إغلاق الطوارئ (Emergency Kill Switch):** هل توجد آلية سريعة لتعطيل موديول معين فوراً (مثل إيقاف بوابة دفع أو إيقاف السحب) دون الحاجة لإعادة نشر الكود بالكامل عند رصد هجوم نشط؟
35. **[SEC-35] خطة الاستجابة للكوارث وتسريب البيانات (Breach Notification Protocol):** هل يمتلك الفريق خطة موثقة لاحتواء الاختراق وإبلاغ العملاء والجهات الرقابية خلال 72 ساعة بموجب القانون؟

---

### قواعد الفيتو الأمني غير القابلة للتفاوض (Absolute Security Veto):
* إذا رسب المشروع في أي فحص من الفحوصات: **[SEC-01 IDOR]** أو **[SEC-03 Mass Assignment]** أو **[SEC-06 JWT Storage]** أو **[SEC-16 Race Condition]** أو **[SEC-20 Leaked Secrets]**، يُشهر زياد فوراً **كرت الفيتو الأحمر ويوقف النشر تماماً** حتى تُعالج الثغرة ويتم التحقق منها باختبار اختراق يدوي.
